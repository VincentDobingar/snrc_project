Par où commencer

4 points critiques exposent aujourd’hui le site à une prise de contrôle de compte admin ou à un XSS visible par tous les visiteurs. Le reste peut suivre un rythme normal de sprint.

Cette semaine — Critique

  • Backend CSRF exploitable sur toutes les routes admin en POST
  • Backend Aucun rate-limiting ni verrouillage sur la connexion admin
  • Backend /auth/refresh ne revérifie pas si le compte est toujours actif
  • Frontend XSS stocké potentiel via contenu riche non assaini

Ce mois-ci — Important (extrait)

  • Backend Routage CRUD dupliqué : FAQ et Settings contournent silencieusement la validation
  • Backend Upload d’image accepte image/svg+xml → XSS stocké possible
  • Backend Validation de fichier basée uniquement sur le mimetype déclaré par le client
  • Backend Aucune sanitisation HTML des champs riches stockés en base
  • Backend Politique de mot de passe faible pour les comptes admin
  • Backend Pas de révocation de session / JWT versionné, PII dans le payload
  • Backend Secrets .env à faible entropie, non bloqués par le garde-fou existant
  • Backend pg.Pool sans gestionnaire d’erreur → risque de crash du process
  • + 17 autres — détail dans les sections ci-dessous

Ce qui est déjà solide

  • Toutes les requêtes SQL du backend sont paramétrées ($1, $2...) — aucune injection SQL détectée sur l’ensemble du code, y compris dans les contrôleurs "admin*" en SQL brut.
  • Le token de session n’est jamais stocké en localStorage/sessionStorage côté frontend — authentification par cookie httpOnly, le bon pattern contre le vol de session via XSS.
  • Le module Recrutement (offres + candidatures + back-office) annoncé comme nouveauté est complet et fonctionnel de bout en bout, sans écart entre promesse et code.
  • L’accordéon FAQ public gère correctement aria-expanded/aria-controls.

Sécurité 14

Critique CSRF exploitable sur toutes les routes admin en POST
src/utils/cookies.js:6-11, src/app.js:39

Le cookie JWT est envoyé avec `sameSite:"none"` en production et aucun jeton CSRF (double-submit ou header dédié) n’est vérifié côté serveur. `express.urlencoded()` est actif globalement. Un formulaire hébergé sur un site tiers peut donc déclencher une requête POST authentifiée (création de compte superadmin, modification de contenu) à l’insu de l’admin connecté qui visite la page piégée.

Recommandation — Ajouter un jeton CSRF (double-submit cookie ou header X-CSRF-Token vérifié serveur), ou n’accepter l’auth par cookie que pour les GET et exiger un Authorization: Bearer pour toute mutation.

Critique Aucun rate-limiting ni verrouillage sur la connexion admin
src/routes/auth.routes.js:9, src/controllers/auth.controller.js:17-51

Rien n’empêche un brute-force sur /auth/login : pas de express-rate-limit ni équivalent dans les dépendances. Combiné à la politique de mot de passe faible (6 caractères minimum), un compte admin est cassable en temps raisonnable.

Recommandation — Ajouter express-rate-limit par IP+email sur /auth/login, avec verrouillage progressif après N échecs.

Critique /auth/refresh ne revérifie pas si le compte est toujours actif
src/controllers/auth.controller.js:63-73

`refresh` récupère l’utilisateur mais ne teste jamais `status !== "active"`, contrairement à `login` qui le fait. Un admin désactivé par un superadmin peut continuer à renouveler sa session indéfiniment via un token déjà émis : la désactivation n’a alors aucun effet réel.

Recommandation — Ajouter la vérification status==="active" dans refresh, et idéalement un token_version en base pour révoquer immédiatement les JWT existants.

Important Routage CRUD dupliqué : FAQ et Settings contournent silencieusement la validation
src/routes/index.js:29-37

adminFaqsRoutes (SQL brut, aucune validation) est monté avant faqRoutes (avec faqValidator) ; adminSettingsRoutes avant settingsRoutes. Express exécute le premier routeur qui matche : en production, POST/PUT /admin/faqs et PUT /admin/settings passent par le contrôleur non validé. faqValidator ne protège donc jamais réellement ces routes malgré son branchement apparent.

Recommandation — Supprimer les implémentations doublons, garder une seule version validée par domaine, et faire échouer le démarrage si deux routeurs déclarent le même chemin.

Important Upload d’image accepte image/svg+xml → XSS stocké possible
src/middlewares/upload.js:32-39,41-47

imageUpload whitelist tout Content-Type commençant par "image/", y compris les SVG. Le fichier est servi statiquement ensuite. Un SVG contenant <script> uploadé via /admin/uploads/image (accessible à un admin_editeur) peut exécuter du JS s’il est ouvert directement dans un navigateur.

Recommandation — Exclure image/svg+xml de la whitelist, ou forcer Content-Disposition: attachment / re-render serveur pour les SVG.

Important Validation de fichier basée uniquement sur le mimetype déclaré par le client
src/middlewares/upload.js:32-39,49-66

file.mimetype vient de l’en-tête multipart fourni par le client, trivialement falsifiable. Aucune vérification des magic bytes n’est faite, ni pour les images ni pour les CV/documents.

Recommandation — Valider le contenu réel du fichier (signature binaire, ex. lib file-type) en plus du mimetype déclaré.

Important Aucune sanitisation HTML des champs riches stockés en base
src/controllers/pages.controller.js:21-28, news.controller.js:25-34, services.controller.js:16-21, jobs.controller.js:25-33

Aucune lib de sanitisation (sanitize-html, DOMPurify+jsdom...) n’est présente. Le contenu HTML riche (pages, actualités, publications, services, offres d’emploi) est stocké brut. Un compte admin_editeur compromis ou malveillant peut injecter du JS persistant visible par tous les visiteurs publics.

Recommandation — Sanitiser content/summary/description côté serveur avant écriture (whitelist de balises), ne pas se reposer uniquement sur le front.

Important Politique de mot de passe faible pour les comptes admin
src/validators/adminUsers.validator.js:6,19

isLength({min:6}) sans aucune exigence de complexité, pour des comptes à privilèges élevés (un superadmin peut créer/supprimer d’autres admins). Combiné à l’absence de rate-limiting, c’est un vecteur de compromission réaliste.

Recommandation — Exiger 10-12 caractères minimum + vérification contre une liste de mots de passe communs (ex. zxcvbn).

Important Pas de révocation de session / JWT versionné, PII dans le payload
src/controllers/auth.controller.js:8-14

Le JWT embarque email, full_name, role, sans jti ni token_version en base. Un changement de rôle ou une désactivation reste sans effet tant que le token n’a pas expiré naturellement (JWT_EXPIRES_IN=1d par défaut).

Recommandation — Ajouter une colonne token_version sur admins, l’inclure dans le JWT et la vérifier dans requireAuth.

Important Secrets .env à faible entropie, non bloqués par le garde-fou existant
src/config/env.js:10-19, .env:11,13

JWT_SECRET et DB_PASSWORD ne sont pas les placeholders connus de .env.example (donc non bloqués par requireSecret) mais suivent un motif prévisible plutôt qu’un secret aléatoire de haute entropie. La protection actuelle ne couvre qu’une liste noire de 3 valeurs connues.

Recommandation — Générer JWT_SECRET avec crypto.randomBytes(64).toString("hex") et exiger une longueur minimale (refuser tout secret <32 caractères) plutôt qu’une simple liste noire.

Mineur Variables d’environnement mortes créant une fausse impression de sécurité
.env:5,17, src/app.js:40

COOKIE_SECRET et API_URL sont définies mais jamais lues dans le code (cookieParser() est appelé sans secret). Donne l’impression que les cookies sont signés alors qu’ils ne le sont pas (le JWT lui-même est signé, donc pas critique).

Recommandation — Nettoyer .env/.env.example ou câbler réellement cookieParser(secret).

Mineur Aucune limite de fréquence sur les formulaires publics contact et candidature
src/routes/messages.routes.js:9, src/routes/jobs.routes.js:22-28

Pas de CAPTCHA ni de rate-limit : spam du formulaire de contact et flood de candidatures (avec upload de fichiers) possibles, avec accumulation de fichiers disque sans nettoyage.

Recommandation — Rate-limit par IP + honeypot/CAPTCHA sur ces deux formulaires publics.

Mineur Un superadmin peut se désactiver/supprimer lui-même sans garde-fou
src/controllers/adminUsers.controller.js:24-46,57-65

update/remove n’excluent pas l’auto-modification ni ne vérifient qu’il reste au moins un superadmin actif après l’opération.

Recommandation — Bloquer la suppression/désactivation du dernier superadmin actif.

Mineur crossOriginResourcePolicy désactivé globalement au lieu d’être ciblé
src/app.js:22-26

La désactivation vise probablement à permettre le chargement cross-origin des fichiers /uploads, mais s’applique à toute l’API, y compris les réponses JSON qui perdent aussi cette protection.

Recommandation — Restreindre crossOriginResourcePolicy:false au seul routeur /uploads via une config helmet dédiée.

Architecture 8

Important pg.Pool sans gestionnaire d’erreur → risque de crash du process
src/config/db.js:6-12

Aucun pool.on("error", ...). Une erreur sur un client idle (coupure réseau, redémarrage DB) émet un événement "error" non intercepté qui peut faire planter tout le process Node selon la doc pg.

Recommandation — Ajouter pool.on("error", (err) => console.error("Pool error", err)).

Important Race condition sur settings (lecture-puis-écriture sans transaction)
src/controllers/adminSettings.controller.js:42-171

Un SELECT décide s’il faut INSERT ou UPDATE, sans BEGIN/COMMIT ni verrou, et aucune contrainte unique n’empêche la duplication. Deux PUT /admin/settings concurrents peuvent chacun voir "aucune ligne" et créer deux lignes de configuration.

Recommandation — Contrainte UNIQUE (singleton id=1) ou INSERT ... ON CONFLICT DO UPDATE dans une transaction.

Important morgan déclaré en dépendance mais jamais monté : logging HTTP absent
package.json:22, src/app.js

Le seul logging est du console.log/error/warn ad hoc dispersé dans le code. Aucune trace structurée des requêtes HTTP en production.

Recommandation — Monter morgan("combined") (ou un logger structuré type pino/winston) avant les routes.

Important Deux systèmes d’erreur/404 concurrents et incohérents
src/middlewares/errorHandler.js, notFound.js vs src/app.js:64-82

errorHandler.js et notFound.js existent comme fichiers dédiés mais ne sont importés nulle part : app.js réimplémente sa propre version inline, avec un format de message différent (champ errors absent dans la version active).

Recommandation — Supprimer les fichiers morts ou les brancher réellement, unifier le format de réponse d’erreur.

Mineur app.js lit process.env.NODE_ENV directement au lieu du module env centralisé
src/app.js:78

Contourne src/config/env.js pourtant utilisé ailleurs (cors.js), créant une incohérence si cette valeur est normalisée un jour dans env.js.

Recommandation — Importer et utiliser env.NODE_ENV partout.

Mineur Pas de pagination ni de plafond sur les listes (pages, news, publications, faqs, messages, jobs...)
src/models/news.model.js:4-11

Number(req.query.limit || 20) sans plafond ni isInt : un appelant peut demander un limit arbitrairement grand, ou une valeur NaN provoquant une 500 au lieu d’une 400 propre.

Recommandation — Ajouter pagination LIMIT/OFFSET avec bornes, valider limit via express-validator.

Mineur Aucun index explicite sur les colonnes de jointure/filtrage fréquentes
sql/schema.sql

Pas de CREATE INDEX sur job_applications.job_offer_id (FK), news.status/published_at, publications.category_id, messages.is_read/status. Postgres n’indexe pas automatiquement les clés étrangères.

Recommandation — Ajouter des index sur ces colonnes, en priorité les FK.

Mineur Pas d’outil de migration versionné
sql/schema.sql, sql/migration_recrutement.sql, sql/sql.sql

Trois fichiers SQL manuels coexistent, appliqués à la main. Pas de suivi de version de schéma, pas de rollback possible.

Recommandation — Adopter un outil de migration (node-pg-migrate, Knex, Prisma...) dès que le schéma évoluera davantage.

Contrairement à Actualités et Carrières, les Publications n’ont pas de route /publications/:slug : chaque document n’est accessible que via un lien direct vers son fichier. Probablement voulu (ce sont des PDF), mais empêche tout partage propre avec métadonnées OG.

Recommandation — Évaluer si une fiche publication apporterait de la valeur SEO/partage, sinon documenter ce choix comme intentionnel.

Méthodologie : lecture manuelle complète du code source (contrôleurs, modèles, routes, validators, composants, pages, configuration) par deux passes indépendantes (backend / frontend), le 17 août 2026. Chaque constat cite un fichier et une ligne précis. Le classement de sévérité reflète l’impact potentiel sur la sécurité, la fiabilité ou l’expérience utilisateur, pas une mesure automatisée.
